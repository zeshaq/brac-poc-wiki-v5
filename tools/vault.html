HashiCorp Vault

DCDR

Secrets store per cluster — Raft-3, transit auto-unseal restored 2026-05-06 (Phase 5) against vault-seed @ .41; DC→DR sync via logical export through MinIO. The export job now uses a scoped periodic token, and OpenShift ESO has a validated smoke path into this Vault service.

What it is

Each cluster runs an independent 3-node Vault Raft cluster, transit auto-unsealed against the vault-seed bootstrap Vault on a small VM at 30.30.30.41. Pod restarts (helm upgrade, node reboot, eviction) come back unsealed automatically — no operator intervention required for normal ops.

The recovery-keys mechanism (5 Shamir shares, 3 threshold per cluster — generated at init time, stored at ~/cloud-init/vault-rke2-{dc,dr}-init-recovery.json) lets operators perform privileged operations (root-token regeneration, seal migration) when both transit and root tokens are unavailable. Day-to-day, these keys are unused.

Phase 5 timeline (2026-05-06):

  • 2026-05-05 — vault-seed VM destroyed (Round-2 decommission); cluster Vaults left as transit-stranded (unsealed in pod memory but unable to restart cleanly).
  • 2026-05-06 ~08:30 — Phase 1 migrated cluster Vaults to per-cluster Shamir (MR !39), defusing the time bomb. Manual unseal required for every pod restart.
  • 2026-05-06 ~13:30 — Phase 5 rebuilt vault-seed at .41 with a fresh transit key (MR !46); both cluster Vaults wiped and re-init'd on transit auto-unseal. Auto-unseal verified by kubectl rollout restart sts vault on both clusters — pods came back unsealed without intervention.

Cross-cluster DC→DR sync continues via the Phase 2 logical replicator (MR !40) running as CronJobs. With transit auto-unseal restored, Raft snapshot ship would also work as an alternative cross-cluster sync mechanism (both Vaults share the same transit key, so master-key decryption works across clusters), but the logical-replication path stays primary because it's already running and gives finer-grained control over what replicates.

Per-cluster keys stay on disk on the operator host (~/cloud-init/vault-rke2-{dc,dr}-init-recovery.json, chmod 600). Edge HAProxy vault-rke2-be backend has DC primary + DR backup; failover happens at the L7 health-check layer (/v1/sys/health?standbyok=true&drsecondaryok=true) within ~9 s on DC pod scale-down.

Configuration

Source of truth: shared/helm-values/vault.yaml (chart-level) and per-cluster overlays at clusters/{dc,dr}/values/vault.yaml.

Replication tooling lives at clusters/{dc,dr}/manifests/vault-replication/ (script ConfigMap + ServiceAccount + CronJob); the vault-replicator Secret with VAULT_TOKEN + MinIO creds is applied imperatively (out of git) — re-apply after any cluster rebuild. VAULT_TOKEN should be a scoped periodic token, not a root token.

Replicator runtime tools (mc + musl-built jq + libonig.so.5) are pre-staged in MinIO bucket vault-replicator-tools (anonymous read), pulled by the CronJob entrypoint via in-cluster wget — avoids the slow public-mirror outbound link.

OpenShift ESO smoke consumer

OpenShift uses this external Vault service as the shared secrets control plane. The OCP-side integration is tracked in the OpenShift wiki, but the Vault-side boundaries are:

  • auth/kubernetes-hub-dc
  • auth/kubernetes-hub-dr
  • auth/kubernetes-spoke-dc
  • auth/kubernetes-spoke-dr

Each auth mount has its own OpenShift API endpoint, CA, TokenReview credential, smoke read policy, and external-secrets role bound to external-secrets/eso-vault-auth. The smoke KV paths live under secret/ocp/eso-smoke/<cluster>.

Validation on 2026-05-06 found SecretStore/rke2-vault Ready=True, ExternalSecret/eso-vault-smoke SecretSynced, and target Secret key message on all four OpenShift clusters. Secret values, Vault tokens, and TokenReview JWTs are not stored in Git or in the wiki.

Operations

Pod restart: with transit auto-unseal, no manual action needed. Pods come up unsealed automatically. If a pod hangs in the seal state, check that the vault-seed-token Secret in the vault namespace is present and that vault-seed at http://30.30.30.41:8200 is reachable.

Recovery operations (regenerate root token, seal migration, etc.) — use the recovery keys at ~/cloud-init/vault-rke2-{dc,dr}-init-recovery.json:

for i in 0 1 2; do
  KEY=$(jq -r ".recovery_keys_b64[$i]" ~/cloud-init/vault-rke2-dc-init-recovery.json)
  vault operator generate-root -nonce=<nonce> "$KEY"
done

vault-seed requires Shamir-unseal after VM reboot — keys at ~/cloud-init/vault-seed-init.txt (3 of 5):

for i in 0 1 2; do
  KEY=$(jq -r ".keys[$i]" ~/cloud-init/vault-seed-init.txt)
  curl -sX PUT http://30.30.30.41:8200/v1/sys/unseal -d "{\"key\":\"$KEY\"}"
done

Trigger an ad-hoc replication round:

kubectl -n vault create job --from=cronjob/vault-replicator-export vri-now

The export CronJob should renew its scoped periodic token automatically at job start. If listing Vault auth methods fails with 403 permission denied or invalid token, rotate only VAULT_TOKEN in vault/vault-replicator with a new scoped periodic token.

Verify replication ran:

mc ls lab/vault-snapshots-logical/dc/ | tail
mc cat lab/vault-snapshots-logical/dc/latest.tar.gz | tar tz

Failover

Edge HAProxy auto-fails over: vault-rke2-be backend has dc as primary and dr as backup; on DC pod scale-down, traffic flips to DR within ~9 s (3× 2 s health-check intervals).

Manual promotion of DR (DC dies for real):

  1. Suspend DR's import CronJob so it stops overwriting live writes:
    kubectl --kubeconfig rke2-dr -n vault patch cronjob vault-replicator-import -p '{"spec":{"suspend":true}}'
  2. HAProxy already routes to DR; apps continue using vault-rke2.apps.sub.comptech-lab.com.
  3. After DC restored: re-init DC vault, do a one-off reverse export from DR / import to DC, resume normal direction.

Known gaps: userpass passwords are NOT replicated (the export captures user metadata but Vault does not expose password hashes via API); reset on DR after import. Identity entities, PKI, transit deferred to v0.2.
