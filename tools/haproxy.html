HAProxy (edge)

Shared infra

L7 edge ingress for the lab — implements DC/DR failover via backup backends.

Quick facts

Form
VM on br30
Failover model
backup keyword per backend (DC primary, DR backup)
DC-primary/DR-backup backends
vault-rke2, keycloak, terrakube-{ui,api,reg}, awx, kafka (SNI passthrough for bootstrap + 3 brokers)
VM backends
gitlab (.5), poc-overview (.130), minio-{api,console} (.14)
Pending DC/DR backends
Nexus, Jenkins, RedisInsight, SigNoz
External IP
160.30.63.134 (br-vm) for app traffic; 160.30.63.138 for the dr.apps subdomain passthrough

What it is

All *.apps.sub.comptech-lab.com hostnames resolve to the HAProxy VM, which fans out to the DC and DR cluster ingress controllers. DC/DR cutover is performed here — there is no DNS movement during failover; clients see at most a single TCP retry.

Architecture

External (160.30.63.134:443)
  │
  ├─ frontend public-apps-http  (port 80)
  │   ├─ ACL is_vm_host  → 301 redirect to https
  │   └─ default → public-apps-http-be (rke2-{1,2,3}:80)
  │
  ├─ frontend public-apps-https (port 443, TCP/SNI mode)
  │   ├─ SNI gitlab.apps        → vm-tls-be → gitlab-vm-be
  │   ├─ SNI minio*.apps        → vm-tls-be → minio-{api,console}-vm-be
  │   ├─ SNI poc-overview.apps  → vm-tls-be → poc-overview-vm-be
  │   ├─ SNI haproxy.apps       → vm-tls-be → haproxy-self-be
  │   ├─ SNI vault-rke2.apps    → vm-tls-be → vault-rke2-be (DC + DR backup)
  │   ├─ SNI auth.apps          → vm-tls-be → keycloak-rke2-be
  │   ├─ SNI terrakube-{ui,api,reg}.apps → terrakube-*-rke2-be
  │   ├─ SNI awx.apps           → vm-tls-be → awx-rke2-be
  │   ├─ SNI bootstrap.kafka.apps / broker-{0,1,2}.kafka.apps → kafka-rke2-be (TCP passthrough; clients do SCRAM_SSL to brokers)
  │   └─ default                → public-apps-https-be (rke2-{1,2,3}:443) ← catch-all for un-named SNI
  │
  └─ frontend public-apps-dr-{http,https} (160.30.63.138, dr.apps.* passthrough to rke2-dr nodes)

The pattern: VM-hosted services keep their own TLS terminator inside HAProxy (vm-tls-be → frontend vm-tls on 127.0.0.1:8443); cluster-hosted services pass SNI through to the cluster's nginx-ingress which terminates TLS itself.

Configuration

Source of truth: /etc/haproxy/haproxy.cfg on the haproxy VM. Edits are applied by SCP-ing the new cfg, running haproxy -c -f /etc/haproxy/haproxy.cfg to validate, then systemctl reload haproxy. Backups land at /etc/haproxy/haproxy.cfg.bak.<timestamp>.<reason> — there are dozens; the most recent are pre-vm-decom (2026-05-05) and pre-kafka-sni (2026-05-06).

HAProxy itself runs on Ubuntu 24.04 in /usr/sbin/haproxy as systemd service haproxy.service. The local TLS terminator on 8443 uses the wildcard cert at /etc/haproxy/certs/wildcard-apps.pem (LE-issued, manual renewal — it's the only cert HAProxy itself owns).

Operations

  • Stats / control socket: echo "show stat" | sudo socat stdio /run/haproxy/admin.sock
  • Force a server into maintenance: echo "set server <backend>/<server> state maint" | sudo socat stdio /run/haproxy/admin.sock
  • Validate a new cfg before reload: sudo haproxy -c -f /etc/haproxy/haproxy.cfg
  • Reload: sudo systemctl reload haproxy — graceful, in-flight connections finish.
  • Self-page (HAProxy reachable check): curl -sk https://haproxy.apps.sub.comptech-lab.com/ hits the embedded nginx on the VM (haproxy-self-be).

Failover

HAProxy itself is single-VM. If the VM dies the whole edge goes dark. Mitigation: KVM snapshot of the VM + the haproxy.cfg backups in /etc/haproxy/; rebuild path is "create-haproxy-vm.sh + restore haproxy.cfg".

For backends, the failover model is per-backend backup keyword: each *-rke2-be backend has DC 30.30.30.{2,3,4}:80 as primary servers and DR 30.30.31.{1,2,3}:80 (or :443 for kafka SNI) as backup servers. Health-check intervals: 2 s for vault, 5 s for keycloak/terrakube/awx, fall=3 (so failover triggers after 6-15 s of failed checks).

Smoke results (all 2026-05-04 / 2026-05-05): Vault 9 s / 30 s, Keycloak 13 s / 18 s, Terrakube 16 s / 65 s, AWX 14 s / 42 s, Kafka L4 instant on broker-pod death.
