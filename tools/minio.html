MinIO

Shared infra

S3-compatible object storage — backs Terrakube remote state, Vault DC→DR logical replication, and the replicator tool stash.

Quick facts

Form
VM on br30 (30.30.30.14:9000)
Buckets (live)
terrakube-state, vault-snapshots-logical (versioned, 14d non-current expiry), vault-replicator-tools (anonymous-read; mc + musl jq + libonig.so.5)
Buckets (planned)
jenkins-rke2-backups, nexus-blobs
Service accounts
vault-replicator-dc (PUT/GET/DELETE on vault-snapshots-logical/dc/*), vault-replicator-dr (GET on vault-snapshots-logical/dc/*)

What it is

Stable S3 endpoint outside both clusters so it's available regardless of which side of DC/DR is current. Application object data on the platform itself uses Longhorn PVCs.

As of 2026-05-06 it also acts as the carrier for Vault cross-cluster sync: DC's vault-replicator-export CronJob ships a logical-export tarball to vault-snapshots-logical/dc/ hourly, DR's import CronJob fetches latest.tar.gz every 4 h and replays into DR Vault. The original vault-snapshots Raft-snapshot bucket plan was abandoned because per-cluster Shamir keyrings can't decrypt each other's master keys (see Vault page).

Architecture

Single MinIO Community server on a dedicated VM at 30.30.30.14. Storage is a single Longhorn-style local disk pool (no erasure coding, single drive) — sufficient for the POC's small object footprint. S3-compatible API on port 9000, web console on 9001. Both ports are exposed via the edge HAProxy as minio.apps.sub.comptech-lab.com and minio-console.apps.sub.comptech-lab.com.

MinIO is intentionally outside both clusters so it remains reachable regardless of which side of DC/DR is current — for cross-cluster artefacts (Vault logical replication, Terrakube state, future backups) we need a stable S3 endpoint.

Configuration

Server config in MinIO env files on the VM (root creds at ~/cloud-init/minio-root-password, chmod 600). Bucket-level configuration (versioning, lifecycle, anonymous access, service-account policies) is done via mc client.

Service accounts and policies (managed via mc admin user/policy):

  • vault-replicator-dc with policy vault-replicator-dc-export (PUT/GET/DELETE on vault-snapshots-logical/dc/*)
  • vault-replicator-dr with policy vault-replicator-dr-import (GET on vault-snapshots-logical/dc/*)
  • terrakube — for Terrakube state, secret at ~/cloud-init/minio-terrakube-secret-key
  • oadp — placeholder for future OADP backups, creds at ~/cloud-init/minio-oadp-credentials
  • signoz — for SigNoz cold-storage future use, creds at ~/cloud-init/minio-signoz-credentials

Anonymous-read on vault-replicator-tools bucket is intentional — pods need to fetch the mc + jq + libonig binaries without SigV4 auth (they don't have mc yet at that point). Set via mc anonymous set download lab/vault-replicator-tools.

Operations

  • Console: https://minio-console.apps.sub.comptech-lab.com — login as zahid with the root password.
  • mc client setup: mc alias set lab http://30.30.30.14:9000 zahid <root-pwd>
  • List buckets: mc ls lab/
  • Inspect a tarball: mc cat lab/vault-snapshots-logical/dc/latest.tar.gz | tar tz
  • Bucket lifecycle: mc ilm rule ls lab/<bucket> shows current rules; add via mc ilm rule add.
  • Service-account audit: mc admin user ls lab/ + mc admin policy entities lab --user <name>

Failover

Single VM, single point of failure for any data that lives only in MinIO (Terrakube remote state, Vault logical-replication tarballs). Mitigation today: KVM snapshot of the VM. There is no MinIO secondary or active-active replication wired.

If MinIO dies during a Vault failover-promotion window, DR's Vault import CronJob will fail (mc cp times out); operators should fall back to manual data replay from any cached tarball.
