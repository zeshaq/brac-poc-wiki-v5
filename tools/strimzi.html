Strimzi operator

DCDR

Kafka operator — manages KRaft Kafka, KafkaUsers, topics, and (on DR) MirrorMaker 2.

Quick facts

Version
0.46.1
Watches
Namespace kafka

What it is

Standard Strimzi install per cluster. Owns the lifecycle of the Kafka CR, the per-user SCRAM credentials (KafkaUser CRs), topic CRs, and on DR the KafkaMirrorMaker2 CR.

Architecture

Strimzi runs in the strimzi-operator namespace per cluster, with cluster role permissions to reconcile Kafka CRs in the watched namespace kafka. It owns the entire Kafka lifecycle: KRaft controller + broker pools, KafkaUsers (SCRAM-SHA-512 credentials), KafkaTopics, and on DR the KafkaMirrorMaker2 CR.

The operator's reconcile loop is what materialises the Kafka cluster from the Kafka CR; we don't directly manage StatefulSets or Services. Editing the CR changes the deployment in place — listener tweaks, advertisedPort changes, broker scale-up all happen via Strimzi.

Configuration

Source: clusters/<cluster>/manifests/strimzi-operator/ (operator install, CRDs included via the operator chart). Once installed, the actual data-plane lives in clusters/<cluster>/manifests/kafka/ as Kafka CR + KafkaUser + KafkaTopic resources.

Watching scope is a single namespace (kafka), set via the operator's STRIMZI_NAMESPACE env. We don't run the operator cluster-wide — keeps RBAC tight and reconciles fast.

Operations

  • Operator pod logs: kubectl -n strimzi-operator logs deploy/strimzi-cluster-operator -f
  • Reconcile a Kafka CR after an edit: it's automatic; for impatience, kubectl -n kafka annotate kafka kafka strimzi.io/manual-rolling-update=true triggers a rolling restart.
  • Pause reconciliation temporarily: kubectl -n kafka annotate kafka kafka strimzi.io/pause-reconciliation=true (e.g. during partial migrations).
  • Upgrade the operator: bump the manifest version in GitOps; the new operator version handles the in-place upgrade of all owned resources.

Failover

Per-cluster — DR has its own Strimzi reconciling DR Kafka. No cross-cluster operator coordination. If the operator pod dies, the existing Kafka cluster keeps serving (operator absence doesn't break the data plane); only schema changes block.
