External Secrets Operator (ESO)

DCDR

Bridges Vault → Kubernetes Secrets. RKE2 platform apps use the in-cluster ESO pattern described here. OpenShift clusters now also use Red Hat ESO with a separate smoke-only Vault integration path into the RKE2 Vault service.

What it is

ESO is the swap-in layer between Vault (source of truth) and the cluster's app workloads. Today most platform apps consume their credentials from imperative Kubernetes Secrets that were planted at install time (e.g. nexus-mavenbot-password, keycloak-admin, terrakube-oidc-secret). ESO replaces those imperative Secrets with Vault-backed ones under the same name — apps don't need any chart-values changes. When a Vault path updates, ESO rewrites the Secret on its next reconcile (default 1 hour) and the app picks up the new value on its next pod restart.

Phase R-G (2026-05-06) is the v0.1 install: Operator + webhook + cert-controller running on both clusters, Kubernetes-auth wired to each cluster's local Vault, ClusterSecretStore CRs landed. Apps are not yet pointed at Vault — that's the per-app onboarding pass starting with Jenkins.

Vault bootstrap (one-time per cluster)

# 1. Enable KV-v2 (already done)
vault secrets enable -path=secret -version=2 kv

# 2. Enable Kubernetes auth
vault auth enable kubernetes
vault write auth/kubernetes/config \
  kubernetes_host="https://kubernetes.default.svc" \
  token_reviewer_jwt="$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt

# 3. Read-only policy for ESO
vault policy write eso-reader - <<'EOF'
path "secret/data/apps/*"     { capabilities = ["read","list"] }
path "secret/metadata/apps/*" { capabilities = ["read","list"] }
EOF

# 4. Bind ServiceAccount → role → policy
vault write auth/kubernetes/role/eso \
  bound_service_account_names=external-secrets \
  bound_service_account_namespaces=external-secrets \
  policies=eso-reader \
  ttl=1h

Done on both clusters 2026-05-06 against each cluster's local Vault. Each Vault has its own Kubernetes auth backend with its own TokenReview JWT and ca.crt — there is no shared k8s identity.

ClusterSecretStore

apiVersion: external-secrets.io/v1
kind: ClusterSecretStore
metadata:
  name: vault-rke2-dc        # vault-rke2-dr on DR
spec:
  provider:
    vault:
      server: http://vault.vault.svc.cluster.local:8200
      path: secret           # KV-v2 mount
      version: v2
      auth:
        kubernetes:
          mountPath: kubernetes
          role: eso
          serviceAccountRef:
            name: external-secrets
            namespace: external-secrets

Cluster-scoped on purpose — any namespace can reference it from an ExternalSecret without per-namespace SecretStore boilerplate. The ServiceAccount is the operator's own SA; ESO uses its TokenRequest API (projected token) to authenticate against Vault on every refresh.

Per-app onboarding (swap-in pattern)

The convention for the platform fan-out (Jenkins → Nexus → AWX → Keycloak → Terrakube → Argo CD):

  1. Read existing Secret data: kubectl -n <ns> get secret <name> -o jsonpath='{.data}' | jq
  2. Write each key to Vault under secret/apps/<app>/<name>: vault kv put secret/apps/jenkins/admin password=$PASS
  3. Drop in the ExternalSecret CR (target name = existing Secret name) so ESO overwrites it with Vault-sourced values
  4. Delete the imperative Secret (or let ESO overwrite it on next reconcile)
  5. Restart the app pod to pick up the new value (only required for envFrom; mounted Secrets reflect on next sync)

Example for Jenkins admin:

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: jenkins-admin
  namespace: jenkins
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-rke2-dc
    kind: ClusterSecretStore
  target:
    name: jenkins-admin-password   # same name app already references
    creationPolicy: Owner
  data:
    - secretKey: jenkins-admin-password   # key inside the K8s Secret
      remoteRef:
        key: apps/jenkins/admin           # under secret/data/apps/jenkins/admin
        property: password                # field inside the KV-v2 entry

DC ↔ DR posture

ESO runs independently per cluster — there is no ESO-level peering. What flows across the WAN is the secret data itself, courtesy of Vault's logical replicator (CronJobs running every 4 h, DC → MinIO bucket vault-snapshots-logical/ → DR import). So:

  • Write a secret to DC Vault → ESO on DC materialises it within ~1 h → DC apps consume it.
  • Same secret reaches DR Vault within ≤ 4 h via the logical replicator → ESO on DR materialises it within ~1 h → DR apps converge.
  • Net DC→DR secret propagation: up to ~5 h. For credentials that need faster propagation, write to both Vaults manually or trigger the replicator on demand.

The DR Vault is read-only from the operator's standpoint (logical-replicator rewrites whatever the DC source wrote). Don't vault kv put on DR directly during normal ops — the next replicator run will overwrite it. During DC outage, the operator can write directly to DR; once DC recovers, reconcile drift manually.

OpenShift ESO relationship

This page describes ESO for RKE2 platform applications. The OpenShift clusters use a separate Red Hat ESO installation from the OpenShift GitOps repo. That OCP integration talks to the same RKE2-hosted Vault endpoint, but it uses one Kubernetes auth mount per OpenShift cluster instead of the RKE2 vault-rke2-dc/vault-rke2-dr ClusterSecretStore model.

The smoke path proves connectivity only. Real OpenShift applications still need namespace-specific Vault policies and roles before app credentials are moved into Vault-backed ExternalSecrets. Do not commit Vault tokens, TokenReview JWTs, or application secret values.

Operations

Health checks

kubectl -n external-secrets get pods
kubectl -n external-secrets logs deploy/external-secrets -f
kubectl get clustersecretstore
kubectl get externalsecret -A
kubectl get externalsecret -A -o wide   # see SyncedSecret + last-refresh

Force a refresh

kubectl -n <ns> annotate externalsecret <name> \
  force-sync=$(date +%s) --overwrite

Common issues

  • SecretSyncedError: permission denied — the eso Vault role isn't bound to the right SA/ns, or the policy doesn't cover the path. Check vault read auth/kubernetes/role/eso and vault policy read eso-reader.
  • SecretSyncedError: namespace not found — the ClusterSecretStore's serviceAccountRef.namespace points to a ns ESO can't see. Should be external-secrets.
  • Stuck OutOfSync in Argo — CRD annotation size exceeds 256KB on ServerSideApply. Worked around in our sync policy with Replace=true.

v0.2 follow-ups

  • Onboard Jenkins (pilot), then Nexus, AWX, Keycloak, Terrakube, Argo CD — see Vault for the secret layout convention.
  • Add PushSecret CRs for the rare app that wants to write back to Vault (default off — ESO is read-only by design here).

  • Promote the ExternalSecret manifests into each app's chart values rather than as standalone files in shared/manifests/.
