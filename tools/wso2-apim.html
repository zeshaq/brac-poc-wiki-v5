What it is

WSO2 API Manager is the API gateway / publisher / developer portal for the platform. v0.1 deploys the all-in-one profile: a single Deployment running gateway + control plane + traffic manager + key manager in one JVM. Future user-deployed demo apps register their APIs with the publisher, consumers discover and subscribe to APIs through the dev portal, and runtime traffic flows through the gateway with token-based auth.

This deployment supersedes the legacy VM-based WSO2 APIM 4.4.0 distributed cluster (apim-{dc,dr}-{cp,tm,gw}-{1,2} — 12 VMs total) that was decommissioned 2026-05-05. The Phase 4 install (2026-05-06) is a clean-slate rebuild on RKE2 — far simpler shape, single pod, smoke-grade.

Per the IdP-strategy memory + ADR-0019: APIM uses its built-in resident KM, not federation to WSO2 IS. Reasons: (1) IS is on H2 with no persistence, so any IS pod restart wipes APIM's KM identity; (2) decoupling lets either IdP fail without taking down the other; (3) v0.2 may federate once IS gets Postgres + persistence.

Architecture

DC cluster (rke2)
─────────────────
Deployment wso2-apim-am-all-in-one (1 replica)
  └─ image docker.io/wso2/wso2am@sha256:7c8bfe…
  └─ embedded H2 file DBs at /home/wso2carbon/.../repository/database/
       ├─ WSO2AM_DB    (apim_db)
       ├─ WSO2SHARED_DB (shared_db)
       └─ WSO2CARBON_DB (registry/local)
  └─ no clustering, no persistence (PVC unwired)
  └─ Resident Key Manager (no IS federation)

Service ClusterIP :9443 (HTTPS) + :9763 (HTTP) + :8243/8280 (gateway)

Ingresses (nginx-ingress, backend-protocol HTTPS):
  ├─ apim.apps.sub.comptech-lab.com    → :9443  (UI: publisher, devportal, admin, carbon)
  └─ gateway.apps.sub.comptech-lab.com → :8243  (API runtime traffic)

cert-manager Certificate apim-tls (clusters/dc/manifests/wso2-apim-prereqs/):
  └─ dnsNames: [apim.apps..., gateway.apps...]
  └─ secretName apim-tls (chart-shared between both Ingresses)

Edge HAProxy (160.30.63.134:443)
  └─ SNI fallthrough → public-apps-https-be → rke2-{1,2,3}:443
     (no dedicated apim-rke2-be backend yet; v0.2)

Future demo apps
  ├─ register APIs in https://apim.apps.../publisher
  ├─ discover/subscribe in https://apim.apps.../devportal
  └─ call gateway at https://gateway.apps.../<context>/<version>/...
       with Bearer access token from /token endpoint

Single replica because: smoke test, embedded H2 doesn't tolerate concurrent writers, simplicity. v0.2 splits into the canonical distributed shape (cp / tm / gw / km separate Deployments) once load patterns warrant.

Configuration

Source of truth: shared/helm-values/wso2-apim.yaml (chart-level values) + clusters/dc/values/wso2-apim.yaml (DC overlay, currently empty placeholder).

Key chart-value overrides:

  • wso2.deployment.image.registry: docker.io + repository: wso2/wso2am + digest: sha256:7c8bfe… — public Docker Hub, pinned by digest (chart only supports digest-based pulls, no tag).
  • wso2.deployment.replicas: 1 + persistentRuntimeArtifacts.enabled: false — single pod, no NFS.
  • wso2.apim.configurations.databases.type: h2 + per-DB JDBC URLs explicit (chart has no H2 default — empty values render as broken connection strings).
  • wso2.apim.configurations.iskm.enabled: false — built-in resident KM.
  • kubernetes.ingress.tlsSecret: apim-tls — shared with both Ingresses; pre-issued by the prereqs Certificate (see below).
  • kubernetes.ingress.{websocket,websub}.enabled: false — WSS / WebSub disabled in v0.1.
  • kubernetes.ingressClass: nginx, all cloud-provider blocks (aws/azure/gcp) enabled: false.

Prereqs Application: clusters/dc/apps/wso2-apim-prereqs.yaml at sync wave 10 applies clusters/dc/manifests/wso2-apim-prereqs/:

  • namespace.yaml — creates the wso2-apim ns.
  • certificate.yaml — cert-manager Certificate covering both apim.apps and gateway.apps as SANs in a single LE cert, written to apim-tls Secret.

Why pre-issue rather than per-Ingress annotations: the chart shares tlsSecret across both Ingresses. Putting cert-manager.io/cluster-issuer on each Ingress would make cert-manager create two Certificate resources both targeting the same Secret — they'd race, and only one of the two hostnames would land in the final cert. Pre-issuing the Certificate explicitly keeps both SANs in one cert.

What's NOT configured yet (v0.2 work):

  • External Postgres (apim_db + shared_db) — currently H2.
  • Persistence on Longhorn RWO so APIs / users / SPs survive pod restart.
  • Admin password rotation (currently admin/admin).
  • Edge HAProxy apim-rke2-be + gateway-rke2-be backends (currently SNI fallthrough).
  • Federation to WSO2 IS as KM (intra-WSO2 pattern from VM era) once IS gets persistence.
  • Bump to APIM 4.7.0 once WSO2 publishes a chart for it (only 4.3.0 is on helm.wso2.com today).
  • Distributed shape (cp / tm / gw / km separate Deployments).

Operations

  • Publisher: https://apim.apps.sub.comptech-lab.com/publisher
  • DevPortal: https://apim.apps.sub.comptech-lab.com/devportal
  • Admin / Carbon: https://apim.apps.sub.comptech-lab.com/admin · /carbon
  • OAuth token endpoint: https://apim.apps.sub.comptech-lab.com/oauth2/token
  • Gateway: https://gateway.apps.sub.comptech-lab.com/<context>/<version>/<resource>
  • Pod logs: kubectl -n wso2-apim logs deploy/wso2-apim-am-all-in-one -f --tail=200
  • Restart: kubectl -n wso2-apim rollout restart deploy/wso2-apim-am-all-in-one — NB: with persistence disabled, all H2 data resets, including registered APIs.
  • Create + publish a sample API (smoke flow): in Publisher → Create API → Type "REST" → set name + endpoint → Lifecycle → Publish. Then in DevPortal → Subscribe with a default-tier app, generate keys, call gateway with the access token.

Failover

None today. DC-only deployment, single replica. If the APIM pod dies, the gateway and management UIs go down until the pod restarts. With persistence disabled, the restart returns a freshly-initialised APIM — registered APIs, users, applications all gone.

Acceptable for smoke testing the gateway / publisher / devportal flows. Once real demo APIs are onboarded, v0.2 hardening (Postgres + persistence) is required so API metadata survives pod restarts.

No DR pair planned for v0.1. If demand grows, follow the Keycloak DC/DR pattern (per-cluster install, edge HAProxy DC-primary/DR-backup, identical realm/keystore on both sides — for APIM that means identical WSO2KEY_STORE_PASS and WSO2_INTERNAL_KEY_STORE_PASS, plus a shared external Postgres so API metadata is consistent).
