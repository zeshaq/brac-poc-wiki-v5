Foundation

webhook-pdns (cert-manager)

DCDR

cert-manager DNS-01 ACME solver that talks to the lab PowerDNS over the API.

Quick facts

Role
DNS-01 challenge solver
Targets
PowerDNS at 160.30.63.133
Zone
sub.comptech-lab.com

What it is

Plugs into cert-manager so wildcard certs and per-host certs in *.apps.sub.comptech-lab.com can be issued from Let's Encrypt without exposing port 80 publicly.

Architecture

Each cluster runs its own webhook-pdns pod in the cert-manager namespace. cert-manager calls the webhook as a Kubernetes APIService extension when it processes a DNS-01 Challenge. The webhook in turn POSTs to PowerDNS's HTTP API at http://160.30.63.133:8081 with the API key, creating a TXT record at _acme-challenge.<host>; once Let's Encrypt validates, cert-manager calls back to delete the record.

Both clusters' webhooks share the same PowerDNS server. The TXT records they write are short-lived (a few seconds) and don't conflict because each Challenge has a unique _acme-challenge token.

Configuration

Source: shared/cluster-issuers/ (the ClusterIssuer references the webhook's GroupName and Solver name) plus clusters/<cluster>/infra/cert-manager-webhook-pdns/ for chart values.

API key for PowerDNS lives in a Kubernetes Secret cert-manager-webhook-pdns in the cert-manager namespace, applied imperatively (out of git). Same key on both clusters since they target the same PowerDNS.

Operations

  • Verify the webhook is registered: kubectl get apiservice | grep acme
  • Watch a Challenge: kubectl get challenges -A -w during cert issuance.
  • Check what TXT records are live in PowerDNS: dig @160.30.63.133 _acme-challenge.<host> TXT +short
  • Webhook logs: kubectl -n cert-manager logs deploy/cert-manager-webhook-pdns

Failover

Per-cluster — DR has its own webhook talking to the same PowerDNS. If PowerDNS is unreachable, both clusters' challenges fail until it's back. There is no DR PowerDNS today (single point for the lab).
