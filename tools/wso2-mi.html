What it is

WSO2 Micro Integrator (MI) is the cloud-native successor to the WSO2 Enterprise Service Bus. It is a stateless mediation runtime: a Docker image plus a Kubernetes-friendly chart that hosts integration artefacts (proxies, sequences, APIs, connectors) authored in WSO2's Integration Studio and packaged as .car (composite application) bundles. Where APIM exposes and governs APIs, MI sits behind APIM and does the actual integration work — protocol translation, message enrichment, routing, calling out to back-end SOAP / REST / database / file / JMS systems on the application's behalf.

This deployment slots into the platform's split-IdP / split-WSO2 model: the application plane gets its own integration runtime (MI), its own API gateway (APIM), and its own IdP (IS), all isolated from the platform-tier Keycloak. Future user-deployed demo apps that need to integrate with non-trivial back-end systems author .car files, push them through the pipeline, and the resulting integration is served from MI; APIM in front exposes them as managed APIs.

v0.1 is intentionally minimal — a single MI pod with the chart's default values, no .car deployments wired in yet, no MI-CTL admin UI hardened, no embedded broker / scheduled-task tuning. It is a clean, ready-to-receive platform; the application engagement adds the integration content on top.

MI is stateless — pod restarts are non-events at the data-plane level (no in-flight message persistence in v0.1). Persistence becomes relevant once .car bundles include scheduled tasks, message stores or inbound endpoints with at-least-once semantics; that is a v0.2 concern.

Configuration

Values live in infra/gitops-rke2, split into a chart-shared file and a DC overlay (consistent with APIM's pattern). This page will be filled in as .car bundles, secret onboarding (ESO from Vault), JKS / truststore handling, and connector packaging are wired up.

  • shared/helm-values/wso2-mi.yaml — chart values shared across clusters.
  • clusters/dc/values/wso2-mi.yaml — DC overlay (currently a thin overlay; expand as integration artefacts arrive).
  • Argo Application: clusters/dc/apps/wso2-mi.yaml (multi-source: chart + values).

v0.2 hardening backlog (open):

  • .car ingestion — mount a deployment-CR config or use the WSO2_SERVER_CARBON_REPOSITORY overlay so packaged integrations land at /home/wso2carbon/wso2mi-4.5.0/repository/deployment/server/carbonapps.
  • Secret material — surface back-end credentials (SAP / DB / MQ) via ExternalSecrets from Vault path secret/apps/wso2-mi/*; never bake into the .car.
  • Truststore / mTLS — pre-load Bank-CA-signed certs and back-end CAs into MI's client truststore.
  • Resource limits — chart defaults are conservative; tune CPU / heap once a representative .car is on board.
  • Edge HAProxy — currently SNI fallthrough via public-apps-https-be; dedicated mi-rke2-be if direct external traffic is wanted (the expected pattern is APIM → MI cluster-internal, so the dedicated backend is optional).
  • DR pair — none today. Add an rke2-dr Argo Application with clusters/dr/values/wso2-mi.yaml once a real .car backlog justifies parity.

Operations

  • Pod logs: kubectl -n wso2-mi logs deploy/cloud-wso2-mi -f --tail=200
  • Restart: kubectl -n wso2-mi rollout restart deploy/cloud-wso2-mi — stateless, ~30 s back to Ready.
  • Management API (mi-ctl): https://mi.apps.sub.comptech-lab.com/management — health, deployed-CAR list, log-level, registered services. Default credentials from chart values; rotate before any real workload.
  • Smoke ping: curl -k https://mi.apps.sub.comptech-lab.com/services/ should return the (initially empty) services listing once the chart's default CAR repo is mounted.
  • Argo: argocd app get wso2-mi — multi-source, expect Synced / Healthy; the values diff lives in the second source.

Failover

None today. Single replica, DC-only, stateless. If the MI pod dies, the kubelet reschedules it; integrations served by MI go down for ~30 s during the rolling restart. Acceptable for v0.1 (no live .car traffic).

v0.2 DR plan: per-cluster install (matching APIM's pattern), edge HAProxy DC-primary / DR-backup, and any .car bundle deployed to DC must also be deployed to DR. Because MI is stateless, "matching configuration" means matching CAR bundles, matching truststore, and matching back-end-system addressability — not data replication.
