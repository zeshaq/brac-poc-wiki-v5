Trivy Operator

DCDR

Continuous in-cluster vulnerability, configuration, secret, and SBOM scanning. DC-only for v0.1. Findings flow to DefectDojo via the hourly trivy-defectdojo-bridge CronJob.

What it is

The Trivy Operator runs as a controller in trivy-system and watches every workload in scope. On pod creation (or scheduled re-scan) it kicks off short-lived Jobs that run aquasec/trivy against the pod's image and Kubernetes manifest, then writes findings as CRDs (VulnerabilityReport, ConfigAuditReport, ExposedSecretReport, SbomReport, RbacAssessmentReport, InfraAssessmentReport). Reports are namespaced and visible via kubectl get vulnerabilityreport -A.

The CRDs are a structured view. DefectDojo's Trivy Operator Scan parser (DD 2.x+) accepts a single CRD object per upload — passing a kind: List wrapper produces 0 findings. The bridge therefore iterates each items[] and POSTs them one at a time, which is why it's a small Python script (image python:3.12-slim) rather than a one-shot curl.

Architecture

Single Deployment (the operator) on each cluster. No DaemonSet for v0.1 (the optional node-collector DaemonSet — which mounts host paths to do CIS/NSA compliance — is disabled). Per-image scans run as transient Jobs scheduled by the operator with a concurrency limit of 5 at a time and a 30 s retry delay; results land in the workload's own namespace.

The data flow: Pod created → Operator schedules scan Job → Trivy container in Job downloads vuln DB and SBOM-extracts the image → writes CRD in workload namespace → bridge CronJob (hourly @:30) lists all CRDs and POSTs each item to /api/v2/import-scan/ with scan_type=Trivy Operator Scan, product_type_name=Platform, product_name="BRAC POC RKE2", engagement_name="trivy-operator-rke2-dc", and a per-item tag. DefectDojo de-duplicates findings within the engagement.

Configuration

Source: shared/helm-values/trivy-operator.yaml + per-cluster overlays in clusters/{dc,dr}/values/trivy-operator.yaml (currently empty — both clusters scan everything by the same rules).

Persistence: a 10 GiB longhorn-r2 PVC mounted by the scanner Jobs to cache the Trivy vuln DB across runs. Without this, every Job re-downloads ~150 MB of DB.

Excluded namespaces are an explicit list (not a label selector) so platform internals don't pollute reports. The exclusion includes defectdojo because we don't need DefectDojo to scan itself for v0.1.

Operations

  • List recent vulnerability reports: kubectl get vulnerabilityreport -A
  • Inspect one: kubectl describe vulnerabilityreport -n <ns> <name> (each report has a report.summary with severity counts plus report.vulnerabilities[])
  • SBOMs: kubectl get sbomreport -A — each carries an embedded CycloneDX SBOM under spec.components, spec.bom
  • Trigger a re-scan for a workload: bump the workload's pod-template hash (any spec change) — the operator detects and rescans
  • Force-run the bridge: kubectl -n trivy-defectdojo-bridge create job --from=cronjob/trivy-defectdojo-bridge bridge-now

Failover

v0.1 is DC-only. v0.2 adds a DR pair (the aquasecurity chart repo needs to be allow-listed in clusters/dr/argocd/projects/rke2-dr.yaml, plus the DR bridge CronJob talking to DefectDojo over the public edge URL). Until then, DR workloads are NOT scanned by Trivy Operator.

If DC's cluster goes down, no aggregation happens until it's back. CRDs persist locally in each cluster's etcd either way.
