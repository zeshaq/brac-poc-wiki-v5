What it is

Standard cert-manager install per cluster. ClusterIssuers are defined once in shared/cluster-issuers/ and applied to both clusters. Certificates issued for *.apps.sub.comptech-lab.com use DNS-01 via the webhook-pdns plugin.

Architecture

cert-manager runs in the cert-manager namespace per cluster, each with its own pair of ClusterIssuers — letsencrypt-staging and letsencrypt-prod. Issuance uses the DNS-01 challenge via the webhook-pdns external solver: Let's Encrypt asks for a TXT record at _acme-challenge.<host>, the webhook writes it into PowerDNS, LE validates, the webhook deletes the TXT record.

DNS-01 is the right choice here because most cluster hostnames live under the wildcard *.apps.sub.comptech-lab.com and aren't directly reachable by Let's Encrypt's HTTP-01 prober. The DNS-01 path requires only that PowerDNS is authoritative for the zone (it is — see PowerDNS).

Configuration

ClusterIssuers live at shared/cluster-issuers/ in the GitOps repo. Each references the webhook-pdns ClusterIssuer-level solvers[].dns01.webhook with the PowerDNS API endpoint and an API-key Secret in the cert-manager namespace.

Most app Ingresses (Keycloak, Terrakube, AWX, Vault, Nexus, Jenkins, RedisInsight, SigNoz, etc.) carry cert-manager.io/cluster-issuer: letsencrypt-prod. Issuance is automatic on first apply; renewals happen ~30 days before expiry without operator intervention.

Operations

  • Inspect a cert lifecycle: kubectl describe certificate <name> -n <ns> shows the CertificateRequest / Order / Challenge chain.
  • Force re-issue: delete the Certificate resource (Argo recreates via Helm chart) or delete the underlying TLS secret.
  • Issuer health: kubectl get clusterissuers — both should report Ready=True.
  • Rate limits: use letsencrypt-staging for any new app under iteration; letsencrypt-prod has 50 certs/week per registered domain.

Failover

cert-manager is per-cluster — DR runs its own copy with identical ClusterIssuers. Each cluster issues certs for its own ingress objects independently. Same hostnames are issued twice (once per cluster) because each cluster's nginx-ingress terminates TLS for its own copy of the app — the active cluster's cert is what clients see at the edge.

If a hostname switches active sides (HAProxy backup keyword), the cert presented changes from the DC LE cert to the DR LE cert. Both are LE-signed and valid; no client reconfiguration needed.
