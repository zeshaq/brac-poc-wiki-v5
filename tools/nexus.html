Sonatype Nexus 3

DCDR

Artifact and container registry for the lab — Maven and NuGet repos live, Docker hosted serving on port 5000, Docker Hub + Quay proxy repos staged, edge DC↔DR failover wired and proven.

What it is

Nexus runs per cluster on Longhorn-backed PVCs. The Docker hosted repo holds internal images (redis-applier already pushed manually; future Open Liberty / NGINX images for the bfsi-poc-openliberty CI flow land here). The Docker Hub and Quay proxy repos are staged to absorb the slow/unreliable upstream pulls that have hurt DR rollouts — pending the connector-port + ingress wiring described under Configuration.

Architecture

Nexus runs per cluster as a single-replica StatefulSet on Longhorn-backed PVCs (data + blob store). Two ingresses per cluster: nexus.apps.sub.comptech-lab.com (UI + REST API on container port 8081) and nexus-docker.apps.sub.comptech-lab.com (Docker registry HTTP connector on container port 5000). The Service exposes both ports; the Docker ingress backends to nexus:5000 and the UI ingress to nexus:8081. Both ingresses carry nginx.ingress.kubernetes.io/ssl-redirect: false so the edge HAProxy → cluster-ingress :80 hop doesn't get 308'd.

Edge HAProxy terminates TLS at vm-tls with the *.apps.sub.comptech-lab.com wildcard cert and forwards plain HTTP to the cluster ingress on :80. Two backends: nexus-rke2-be (UI/REST) and nexus-docker-rke2-be (registry), each with DC primary (30.30.30.2:80) + DR backup (30.30.31.1:80). Health-check paths: GET /service/rest/v1/status (200) and GET /v2/ (401 — the auth-required state is the healthy state). timeout server 30m on both backends to handle large image-layer + Maven artefact uploads.

Configuration

Source: clusters/<cluster>/manifests/nexus/ — Namespace, StatefulSet, Service, Ingress (regular + Docker), Certificate, PVC, plus the legacy nexus-provisioning ConfigMap of Groovy scripts (functionally inert: Nexus 3.74 does not auto-execute scripts mounted at /opt/sonatype/nexus/etc/scripts; live config is provisioned via REST).

Repos created via REST API (POST /service/rest/v1/repositories/<format>/<type>) on each cluster:

  • docker-hosted — HTTP connector :5000, v1Enabled: false, forceBasicAuth: true, writePolicy: ALLOW_ONCE. Listens on container port 5000 inside the pod; reachable through the nexus-docker.apps... ingress at /v2/.
  • docker-hub-proxy → https://registry-1.docker.io, indexType: HUB. Staged but not pullable by docker clients yet: no connector port, and the single docker ingress is owned by docker-hosted on :5000.
  • docker-quay-proxy → https://quay.io, indexType: REGISTRY, indexUrl: https://quay.io. Same caveat as the Hub proxy.
  • Maven set: maven-releases, maven-snapshots, maven-central (proxy), maven-public (group).
  • NuGet set: nuget-hosted, nuget.org-proxy, nuget-group.

Why no docker-group: a single-port group with a writable hosted member would let clients use nexus-docker.apps.../<image> for both push and pull-through-cache. Nexus rejected it: Deploying to groups is a PRO-licensed feature. Two ways forward without Pro: (a) accept the proxies-only-for-pull split and add new ingresses + container ports (e.g., :5001 hub, :5002 quay) so docker clients can target them directly; (b) live without proxies and continue to ctr import for upstream-pull pain. Path (a) is the planned follow-up.

CI bot users + roles (created on both clusters with the same passwords):

  • mavenbot — role cicd-maven: privileges nx-repository-view-maven2-*-{read,browse} + nx-repository-view-maven2-maven-{snapshots,releases}-*. For Jenkins Maven deploy.
  • jenkinsbot — role cicd-docker: privileges nx-repository-view-docker-*-{read,browse} + nx-repository-view-docker-docker-hosted-*. For Jenkins docker login + push.

Auth: bootstrap admin UUID at /nexus-data/admin.password on the pod is still the active admin credential (wizard never completed); rotation is a separate deliberate follow-up. OIDC via Keycloak's nexus client is wired in the realm but not yet activated in Nexus.

Operations

  • UI: https://nexus.apps.sub.comptech-lab.com
  • Docker registry health: curl -skI https://nexus-docker.apps.sub.comptech-lab.com/v2/ — healthy state is HTTP/2 401 with WWW-Authenticate: BASIC and Docker-Distribution-Api-Version: registry/2.0. HTTP 502 means the connector is down or the docker repo was deleted.
  • Docker login (CI): docker login nexus-docker.apps.sub.comptech-lab.com -u jenkinsbot using the password from ~/cloud-init/nexus-jenkinsbot-password.
  • Push image: docker tag <src> nexus-docker.apps.sub.comptech-lab.com/<name>:<tag> && docker push nexus-docker.apps.sub.comptech-lab.com/<name>:<tag>
  • Maven deploy (CI): mvn deploy -DaltDeploymentRepository=snapshots::default::https://nexus.apps.sub.comptech-lab.com/repository/maven-snapshots/ with ~/.m2/settings.xml <server> id=snapshots, username=mavenbot, password=<…>.
  • List repos via REST: curl -sk -u admin:<pw> https://nexus.apps.sub.comptech-lab.com/service/rest/v1/repositories
  • Re-create the docker-hosted repo (if ever lost): POST /service/rest/v1/repositories/docker/hosted with body {name, online, storage{blobStoreName, strictContentTypeValidation, writePolicy}, docker{v1Enabled:false, forceBasicAuth:true, httpPort:5000}}. Restart not required — the connector binds immediately.
  • Backups: planned MinIO bucket nexus-blobs (CronJob not yet created — STATE.md TODO).

Failover

Service availability: edge HAProxy nexus-rke2-be and nexus-docker-rke2-be with DC primary + DR backup. When DC ingress goes unhealthy, the same FQDNs (nexus.apps... and nexus-docker.apps...) silently switch to DR. Both clusters are independently provisioned with the same repos, same realms, and the same mavenbot/jenkinsbot passwords — so a Jenkins credential authored once works against either side post-failover. Verified 2026-05-06 with admin-socket DISABLE on the DC servers: cutover transparent, jenkinsbot auth + /v2/ 200 served by DR, /service/rest/v1/status 200 throughout; re-enable returned both backends to UP within seconds.

Data continuity: not automated. Pushed Maven artefacts and Docker images on DC are not replicated to DR. The placeholder nexus-sync-from-dc CronJob in the DR namespace currently does nothing. The intended pattern is build-once + push-to-both, or ctr import to bypass the registry. Replicating Nexus blob storage cross-cluster is a future Phase R-G concern.
