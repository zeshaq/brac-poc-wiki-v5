Redis operator (Spotahome)

DCDR

Reconciles RedisFailover CRs — Sentinel-managed Redis primaries with replica failover.

Quick facts

Project
Spotahome redis-operator
Version
3.2.13

What it is

Standard Spotahome operator install per cluster. Owns the lifecycle of the RedisFailover CR including Sentinel quorum, primary election, and rolling restarts.

Architecture

Spotahome's redis-operator runs in redis-operator namespace per cluster. It watches RedisFailover CRs and reconciles them into a primary + N replicas Deployment plus a 3-node Sentinel quorum. Sentinel handles primary election; clients do their initial Sentinel-aware connection (talk to Sentinel, get current primary) instead of pinning a DNS name.

The operator does NOT manage cross-cluster replication. That layer is handled by the Kafka WAL pattern (redis-applier + MirrorMaker 2) — see Redis. Each cluster has its own independent RedisFailover.

Configuration

Source: clusters/<cluster>/manifests/redis/ — operator install + RedisFailover CR + Service overrides. The CR specifies replica count, image, resources, persistence, and Sentinel quorum config.

The RedisFailover CR for this lab uses the default no-auth posture (no requirepass); access control rides at the Kubernetes / NetworkPolicy layer. If we re-enable auth, set it via the CR's auth stanza which picks up a Secret.

Operations

  • Operator status: kubectl -n redis-operator get pods
  • RedisFailover health: kubectl -n redis get redisfailovers.databases.spotahome.com shows phase per CR.
  • Force a Sentinel-driven failover: kubectl -n redis exec rfs-redis-0 -- redis-cli -p 26379 sentinel failover redis-master
  • Inspect Sentinel state: kubectl -n redis exec rfs-redis-0 -- redis-cli -p 26379 sentinel masters

Failover

Per-cluster — the operator manages in-cluster Redis failover via Sentinel. DC↔DR Redis durability is the Kafka WAL story, not the operator's responsibility.
